# Supabase client contract

Apply all files in `migrations/` in timestamp order. All IDs UUID. Dates `YYYY-MM-DD`; timestamps ISO UTC; outlet and attendance use Asia/Jakarta. Client may read tables but employee/attendance/leave writes must use RPC. All RPCs return a row object unless described otherwise. Failure is a Postgres error with Indonesian message; show that message to the user, never mark a failed mutation as successful.

## Tables

- `departments`: id, name, active.
- `positions`: id, department_id, name, is_cashier, active.
- `outlets`: id, code, name, address, latitude, longitude, radius_m (default100), max_accuracy_m(default100), opens_at, closes_at, morning_starts_at(default07:00), afternoon_starts_at(default15:00), late_tolerance_minutes(default0), production_location, active.
- `employees`: id, employee_number(autoRK000001), auth_user_id, full_name, whatsapp, department_id, position_id, outlet_id, approver_employee_id, approval_mode(`internal`/`external`), starts_on, employment_type(`permanent`), status(`active`/`inactive`), account_status(`uninvited`/`pending`/`active`/`disabled`), ends_on, exit_reason, can_clock, can_middle_shift, weekly_off_days(int[];0=Sunday), birthday, gender(`male`/`female`/`unspecified`), address, emergency_name, emergency_phone, photo_path.
- `employee_roles`: employee_id, role(`employee`/`admin_hr`/`head_baker`). Approver permission comes from the relationship, not HR role.
- `attendance`: id, employee_id, outlet_id, work_date, shift(`morning`/`afternoon`/`middle`), expected_in(nullforMiddle), expected_out, clock_in, clock_out, selfie_path, late_minutes, worked_minutes, in_distance_m, out_distance_m, corrected, source(`clock`/`manual`). Manual records have null selfie/GPS evidence and must be visibly labeled as HR entries. Remaining snapshot/location fields available for recap.
- `cashier_assignments`: one dated roster row per employee, outlet, shift(`morning`/`afternoon`/`middle`/`off`), status(`active`/`cancelled`), reason, actor and timestamps. `planned_starts_at`/`planned_ends_at`/`planned_ends_next_day` are an explicit planning snapshot; Pagi/Sore derive from outlet schedule on write, while Middle remains unknown until Admin HR records an eight-hour plan. Keep this schedule separate from actual `attendance`.
- `staffing_requirements`: outlet, weekday(0=Sunday), shift, minimum(0-100), `effective_from`, actor and timestamps. No row means not configured; minimum zero means no staffing target. Admin HR can read; save with `staffing_requirement_save`.
- `cashier_roster_batches`: private idempotency receipt and committed result for one actor/request key. No direct client access; write through `cashier_roster_batch_save` only.
- `spv_followups`: unique source case, issue type, work date/outlet/employee/shift, owner, status(`new`/`in_progress`/`completed`), note, resolution, reopen count, `revision`, optional `due_at`, and audit timestamps. Admin HR can read through the paged backlog RPC; all changes use the revisioned follow-up RPCs.
- `supervisor_capabilities`: scoped employee capability for an outlet and optional issue category. It separates operational authorization from job title. Capabilities include issue report/view/handle/configuration, handover monitoring, report visibility, and coverage configuration. Each grant has a monotonic `revision` and `updated_at` for configuration concurrency.
- `supervisor_issue_categories` / `supervisor_issue_routes`: Admin HR maintained category and recipient routing, each with a monotonic `revision`. Use the category catalogue RPC for reporting; routes snapshot the recipient at issue creation. Private configuration receipts preserve exact idempotent v2 results per actor/key.
- `outlet_issues` / `outlet_issue_events`: versioned outlet issue, its immutable event history, optional private photo reference, assigned handler, due time, and resolution. A recipient whose handling capability has since been revoked is not assigned to a new report; its routing snapshot remains for traceability and the issue enters the unassigned queue. A configured recipient is validated as that target employee in the requested outlet/category scope, never by treating the configuring Admin HR's own authority as the target's capability. Never write these tables directly.
- `shift_handovers` / `shift_handover_versions` / `shift_handover_events`: sender/recipient handover and immutable version history. A sent handover must name an active, assigned recipient. The selected recipient alone may acknowledge or request revision; either response advances the version and writes the snapshot that was confirmed.
- `shift_exchange_requests` / `shift_exchange_events`: request to swap or replace a scheduled cashier. A peer response and a non-participant Admin HR decision are required before roster rows change. The requester may cancel only while it is pending; Admin HR may explicitly expire stale pending requests. Active requests are unique for a requester assignment and for a peer/day. Replacement candidates are revalidated for active account, cashier clock permission, Middle permission where needed, attendance, and approved full-day leave at submission and again before final approval.
- `staffing_interval_requirements`: explicit non-overlapping outlet/day-of-week time intervals, effective-date range, minimum staffing, revision and audit. A scoped configurator may read its own outlet's interval configuration and redacted coverage, but an update must authorize both the old and requested outlet, carry a non-null matching revision, and cannot rewrite an already-effective interval. It supplements but never silently converts legacy `staffing_requirements`.
- `leave_requests`: id, employee_id, kind(`annual`/`personal`/`sick`), extent(`full_day`/`late_arrival`/`temporary_exit`/`early_departure`), starts_on, ends_on, starts_at, ends_at, reason, status(`pending`/`approved`/`rejected`/`cancelled`/`needs_info`), deductions(year->daysJSON), decision_by, external_decider, decision_note, decided_at, created_at.
- `leave_adjustments`: id, leave_request_id, type(`change`/`cancel`), starts_on, ends_on, starts_at, ends_at, reason, status(`pending`/`approved`/`rejected`), decision_by, external_decider, decision_note, decided_at.
- `leave_ledger`: immutable signed amount; negative deduction/positive refund, year. Never insert directly.
- `audit_events`: actor_employee_id, entity, entity_id, action, reason, before_data, after_data, created_at. HR-only read.

## Auth Edge Function `hr-api`

Call `supabase.functions.invoke('hr-api',{body:{action,...}})`; public login/activation work with publishable/anonkey.

- `login`: employee_number,password -> `{session,user}`. Set Supabase session with access_token and refresh_token. Employee number case-insensitive. Only active linked accounts work.
- `issue_activation` / `issue_reset`: employee_id; authenticated AdminHR -> `{url,expires_at,employee_number,full_name,message}`. URL can be copied into WhatsApp manually; it is not sent.
- A token currently being consumed cannot be replaced during its five-minute claim lease. HR can replace abandoned/expired claims afterward; the old token is revoked and cannot finalize. This prevents worker failures from permanently blocking activation/reset.
- `activate` / `reset_password`: token,password -> `{ok:true,employee_number}`. Password >=10 characters. Then log in normally.
- `inspect_token`: token -> `{purpose,employee_number,full_name,expires_at}` for activation form. No DB write.
- `bootstrap`: bootstrap_secret,full_name,whatsapp,password,outlet_name -> `{ok:true,employee_number}`. Server `HR_BOOTSTRAP_SECRET` must be at least32characters, works only before an AdminHR exists. Creates initial admin and the provided outlet with coordinates unset; department/position structure is seeded by migration. Remove bootstrap secret after success. Configure the outlet coordinates before clock in can work.

Server-only env: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `APP_ORIGIN` (canonical frontend origin), optional `HR_BOOTSTRAP_SECRET`. Edge verifier disabled because actions explicitly verify user JWT when needed. No servicekey goes to browser.

## Authenticated RPC

- `employee_directory()` -> active employee array with safe id,employee_number,full_name,department_id,position_id,outlet_id,approver_employee_id,approval_mode,status,can_clock,can_middle_shift. Use these work fields to resolve names and team approval relationships. Private profiles remain readable only by their owner/AdminHR; directory omits phone, address, birthday, start date and login identity. Approvers obtain team balance with `leave_balance`, not a local calculation from private start date/ledger.
- `hr_save_employee({p_employee:object,p_id:null|uuid,p_reason:string})` -> employee. Work snake fields permitted; auth_user_id/employee_number/account_status not permitted. New employee gets `employee` role. Use `hr_set_roles({p_employee_id,p_roles:['admin_hr',...]})` separately. Own roles cannot be changed.
- `update_my_profile({p_profile:{address,emergency_name,emergency_phone,photo_path}})` -> employee.
- `attendance_clock_in({p_shift,p_latitude,p_longitude,p_accuracy_m,p_selfie_path})` -> attendance. First upload new camera JPEG to private `attendance-selfies` at `${auth.uid()}/${crypto.randomUUID()}.jpg`. Server checks distance, accuracy, ownership, photo presence, employee permissions and concurrent duplicates. Clock in/out are database time.
- `attendance_clock_out({p_latitude,p_longitude,p_accuracy_m})` -> attendance. Resolves open session automatically including across midnight.
- `attendance_correct({p_id,p_clock_in,p_clock_out,p_reason,p_shift:null|'morning'|'afternoon'|'middle'})` -> attendance; HR-only, no own correction; original saved in audit. Use ISO timestamps, null clockout allowed. Shift correction recalculates lateness from original outlet schedule snapshots, not today's settings.
- `attendance_record_manual({p_employee_id,p_shift,p_clock_in,p_clock_out:null|ISOtimestamp,p_reason})` -> attendance; HR-only, no own entry. For failed GPS/camera or forgotten clock in with no existing row. Reason must have at least five characters; work date derives from supplied time in Asia/Jakarta. Times cannot be in the future and duplicate/overlapping records are rejected. Uses current employee outlet settings, preserves a schedule snapshot, `source:'manual'`, `corrected:true`, and an audit event. It records no fabricated GPS or selfie. Correct an existing row with `attendance_correct` instead.
- `staffing_requirement_save({p_outlet_id,p_weekday:0..6,p_shift,p_minimum:0..100,p_effective_from})` -> requirement; Admin HR only. Effective date must be today or later. Use a new effective date for a future change so earlier coverage remains explainable; editing an existing outlet/day/shift/date updates that entry and keeps its before/after audit.
- `cashier_roster_batch_save({p_week_start:Monday,p_idempotency_key,p_changes:[{id,employee_id,work_date,outlet_id,shift,reason,expected_updated_at,cancel}]})` -> `{batch_id,week_start,saved_count,assignments}`. Admin HR only, 1-500 unique employee/date changes, today or future in that Monday-Sunday week. Existing row id and `updated_at` must match the preview. Server checks active cashier/outlet, start date, Middle permission, full-day approved leave, no existing attendance and no self-assignment. Every row, audit record, idempotency result and one `assignment_week` inbox notification per active recipient commit or roll back together. Retrying the same actor/key/payload returns the original result; reusing the key with another payload fails. `cancel:true` cancels an existing active row. Do not write roster or batch tables directly.
- `spv_followup_start({p_issue_type,p_work_date,p_outlet_id,p_employee_id,p_shift,p_source_type,p_source_id})` -> follow-up row. Admin HR only. The server checks that the referenced condition still exists before opening/reopening a durable case; duplicate refreshes reuse the same case. It never creates or changes attendance, leave or deductions.
- `spv_followup_page({p_view:'all_open'|'mine'|'unassigned'|'overdue'|'history',p_outlet_id?,p_from?,p_to?,p_page_size?,p_cursor?})` -> `{items,total,has_more,next_cursor,as_of}`. Admin HR only; the default is a bounded stored-case backlog, not all historical source data.
- `spv_followup_update_v2({p_id,p_expected_revision,p_idempotency_key,p_status:'new'|'in_progress'|'completed',p_owner_id,p_note,p_resolution_note,p_due_at,p_reason})` -> follow-up row. Admin HR only. Expected revision is mandatory; same key/payload returns the committed original result, while the same key with another body and stale revisions are rejected. In-progress requires an active Admin HR owner; completion requires a resolution note; changes are audited. A completed case reopens only when its source condition recurs. The former `spv_followup_update` endpoint is deliberately fail-closed so clients cannot omit version checking.
- `supervisor_issue_category_page({p_include_inactive:false})` -> active category catalogue. An active employee may read active categories; inactive categories require Admin HR. `supervisor_operation_configuration_page()` is Admin HR-only and returns category/route/capability snapshots with their server revisions. New configuration writes use `supervisor_issue_category_save_v2`, `supervisor_issue_route_save_v2`, and `supervisor_capability_save_v2`: expected revision is required for an existing row, an idempotency key and exact request hash protect replay, stale/new-conflicting writes fail with a conflict, and audit is transactional. New capability grants have no old baseline; revocations require the exact existing ID/revision and matching scope. The legacy `supervisor_issue_category_save`, `supervisor_issue_route_save`, and `supervisor_capability_save` remain only for transition compatibility and advance the same revision so they cannot silently bypass a v2 baseline.
- `outlet_issue_submit({p_outlet_id,p_category_id,p_description,p_urgency:'low'|'normal'|'high'|'urgent',p_photo_path?,p_reporter_employee_id?,p_idempotency_key})` -> issue. The reporter must be active and may nominate another reporter only with scoped capability. Routing eligibility is checked again at insert; a revoked/missing handler produces an unassigned issue with a preserved route snapshot, rather than assigning stale authority. `outlet_issue_page` returns only reporter/creator or capability-scoped work. `outlet_issue_update_v2` requires expected revision, key, status, owner, due time, resolution and reason; it atomically writes issue/event/audit/notification and retains exact replay semantics.
- `shift_handover_save_v2({p_id?,p_expected_version?,p_idempotency_key,p_outlet_id,p_work_date,p_sender_assignment_id,p_recipient_employee_id,p_recipient_assignment_id,p_pending_work,p_outlet_condition,p_notes,p_send,p_reason})` -> handover. `p_send:true` requires a valid recipient on creates and updates. `shift_handover_respond_v2({p_id,p_expected_version,p_idempotency_key,p_accept,p_reason})` can be called only by the selected recipient; its accepted/revision-requested response advances the handover version and persists a corresponding version snapshot. Both retain audit and exact replay receipts.
- `shift_exchange_submit({p_request_type:'swap'|'replacement',p_requester_assignment_id,p_peer_employee_id,p_reason,p_idempotency_key})` -> request. `shift_exchange_respond_v2` requires the selected peer. `shift_exchange_decide_v2` requires a non-participant Admin HR, expected revision, key, decision and note; it atomically swaps row context or creates/cancels the replacement roster entry. Submit and final decision recheck attendance, full-day approved leave, Middle eligibility, and the planned-start snapshot deadline. A trigger locks and rechecks both parties for full-day leave on pending/approved writes. For replacement, the target is additionally rechecked at submit and final approval for active/account-active state, `can_clock`, Middle entitlement for a Middle requester, attendance, and full-day leave; a pending request does not grandfather a stale candidate. `shift_exchange_cancel_v2({p_id,p_expected_revision,p_idempotency_key,p_note})` is requester-only and only while pending. `shift_exchange_expire_stale_v2({p_idempotency_key})` is Admin HR-only; it atomically closes only pending rows whose work date has passed and persists one `{expired_count,as_of}` receipt result, so a retry returns the original result rather than a new timestamp. Both record event/audit/notification and retain exact replay receipts. Do not update roster directly as a substitute.
- `staffing_interval_requirement_save_v2({p_id?,p_expected_revision?,p_idempotency_key,p_outlet_id,p_weekday,p_starts_at,p_ends_at,p_minimum,p_effective_from,p_effective_until?,p_reason})` -> requirement. New intervals cannot backdate; updates lock the old row, require a non-null matching revision and authorization over old and new scopes, serialize overlap checks, and reject rewriting an interval already in effect. For an update, scope authorization is rechecked before the receipt lookup; the exact same actor/key/payload can then replay its committed result after a later revision, while a caller whose access has since been revoked is still denied. `cashier_assignment_plan_save_v2({p_assignment_id,p_expected_updated_at,p_idempotency_key,p_starts_at,p_ends_at,p_reason})` plans active Middle only and requires exactly eight hours including break; it also rejects legacy attendance rows that lack `assignment_id`. `supervisor_interval_coverage({p_outlet_id,p_work_date})` keeps planned, leave-adjusted available, recorded attendance, shortages, and unplanned Middle separate; employee identities remain redacted unless the caller is Admin HR. `supervisor_report_page({p_from,p_to,p_outlet_id?,p_employee_id?})` accepts at most 63 days and returns a traceable aggregate/details; it never returns private leave/selfie documents.
- `leave_balance({p_employee_id:null|uuid,p_year:2026})` -> `{year,allowance,used,remaining,expired}`. Entitlement computes calendar three months with first eligible month counted full; each new year independent. `expired:true` means no spendable balance even if historical remaining positive.
- `leave_submit({p_kind,p_starts_on,p_ends_on,p_reason,p_extent:'full_day',p_starts_at:null,p_ends_at:null,p_attachment_path:null})` -> request.
- Partial-day requests use one date. `late_arrival` and `early_departure` accept the relevant time in `p_starts_at` (single input; `p_ends_at:null`). `temporary_exit` requires both `p_starts_at` and a later `p_ends_at`. The same validation applies when proposing date/time changes. Approved late-arrival requests and their times remain available to recap alongside actual `late_minutes`; approval does not silently erase actual lateness.
- `leave_decide({p_id,p_decision:'approved'|'rejected'|'needs_info',p_deductions:{'2026':2},p_note:null,p_external_decider:null})` -> request. EmptyJSON means no deduction. Non-own approver only; for externalapproval, anotherAdminHR records externalname.
- `leave_request_change({p_id,p_starts_on,p_ends_on,p_reason,p_starts_at:null,p_ends_at:null})` -> `{request,adjustment}`. Pending request edits immediately; approved creates pending adjustment preserving olddates/balance.
- `leave_request_cancel({p_id,p_reason})` -> `{request,adjustment}`. Pending directcancel, approved pending adjustment preserving oldrequest.
- `leave_decide_adjustment({p_id:adjustmentUUID,p_approved:boolean,p_deductions:{'2026':1},p_note:null,p_external_decider:null})` -> adjustment. New deduction total (notdelta); cancellation ignores deductions and refunds old charge to originalyear. Reject leaves original untouched. Transactions lock employee balance; duplicate decisions rejected.

For crossyear requests, UI must split total deduction by year explicitly. Always show allocation before approval. Final sum may be dynamic; DB validates each year's remaining. Refund from an expiredyear is recorded historically and never becomes nextyear balance.

Realtime tables: employees,attendance,leave_requests,leave_adjustments,cashier_assignments,attendance_correction_requests,notifications,staffing_requirements,spv_followups,outlet_issues,shift_handovers,shift_exchange_requests,staffing_interval_requirements. Re-fetch through the paged supervisor RPC after changes, reconnect, or app resume; do not merge a realtime callback over a local draft/pending attempt. Inbox entity types include `assignment_week`, `spv_followup`, `outlet_issue`, `handover`, and `shift_exchange`; bodies are generic and authenticated hrefs open the relevant item. All private tables require active account via RLS, including JWTs retained after disabling profile. Selfie signed URL may be obtained only by employeeowner/AdminHR; cache neither privatephotos nor signedURLs in serviceworker.

Optional leave evidence uploads to private `leave-attachments` at `${auth.uid()}/${crypto.randomUUID()}.jpg` (JPEG/PNG/WebP/PDF,max5MiB); p_attachment_path is validated against actual uploaded object and current owner. Read allowed to employeeowner, assignedapprover, AdminHR. Profile photos use private `profile-photos` with same ownerpath and max5MiB imageformats; employee/HR only. Uploads cannot be overwritten. Active owners may remove unused uploads after a failed save; RLS denies deleting objects referenced by any attendance, leave request or employee profile, even when that reference is hidden from the owner by RLS. HR cannot remove another user's upload.

Outlet-issue evidence uses private `outlet-issue-photos` at `${auth.uid()}/${crypto.randomUUID()}.jpg|jpeg|png|webp`. Upload ownership is checked before issue submission; reads require reporter/creator or scoped issue access, and a referenced photo cannot be deleted. Do not cache signed URLs or photo bytes in the service worker.

Master tables support `.insert`/`.update` for HR. No delete; set active=false. UI validates emptyfields. Positions is_cashier is a form convenience; set employee can_clock explicitly and server permission remains authoritative.

## Supervisor hardening preflight

For an upgrade from the actual Preview baseline, first apply migrations 19–21, then run the read-only [preflight-supervisor-operational-hardening.sql](deployment/preflight-supervisor-operational-hardening.sql) while history is exactly migrations 1–21, then apply migrations 22 and 23 in source order. The preflight checks duplicate active exchange rows that would violate the two partial unique indexes. It is safe to repeat when clean; when duplicates exist it fails closed and never cancels, expires, deletes, or rewrites an operational request. Migration 22 repeats the same fail-closed condition so a one-step push cannot silently alter data. This path is distinct from the historical 13-migration preflight, which must still run before its earlier incompatible migration.

## Versioned supervisor configuration

Configuration v2 is Admin HR-only and uses `private.supervisor_configuration_receipts`, which is never readable by clients. The client must retain the original key and payload for an ambiguous response, reload the configuration snapshot before starting a new edit, and submit the newer server revision after an explicit conflict review. An old client may temporarily invoke the legacy save RPCs, but those writes advance the same revision; therefore the next v2 save conflicts safely instead of overwriting it. Direct table writes do not replace the RPC contract.
